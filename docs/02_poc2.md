# 세션 1 — PoC #2: 스크립트 «문자열 예산» 규칙 (2026-08-25)

## 질문

PoC #1 로 확인된 건 **「원본과 정확히 같은 바이트 수」**뿐이다.
번역문이 원본보다 길어지는 줄은 반드시 나오므로, 다음을 갈라야 한다.

- 메시지 하나를 늘리고 다른 메시지를 줄여 **구간 총량만 맞추면** 되는가?
- 아니면 어딘가에서 **절대 오프셋**으로 메시지를 가리켜서, 1바이트만 밀려도 깨지는가?

## 확인된 바이트코드 구조 (정적 분석)

`DATASCR.BIN` 은 **순차 실행 VM 바이트코드**이고 문자열은 **인라인**이다.

```
0xa426  10  <33B SJIS>  00     ; 少女「なつかしい\n　いつもの景色。
0xa449  01 03                  ; (제어)
0xa44b  10  <51B SJIS>  00     ; 　やっと帰ってこれたんだわ。\n　１年ぶりの故郷……。
0xa480  01 61 22 ...           ; 다음 명령
```

- `0x10` = 메시지 출력, 인자는 **NUL 종단 SJIS**, 개행 `0x0A`.
- 인라인이므로 **문자열을 가리키는 포인터가 없다** — 대신 길이가 바뀌면 그 뒤가 통째로 밀린다.
- ⚠️ 그래서 **종단자를 앞당기는 «단순 단축»은 위험하다**. NUL 뒤의 남은 원문 바이트가
  그대로 «명령»으로 실행된다. 짧게 쓰려면 남는 자리를 채우거나 구간을 재조립해야 한다.

## 실험 — 인접 메시지 간 «예산 이동»

구간 `0xa426..0xa480`(90B)을 통째로 재조립했다. **구간 총량은 그대로**, 안에서만 옮겼다.

| | 원본 | 패치 | 증감 |
|---|---|---|---|
| 메시지 1 | 33 B | **39 B** | **+6** |
| 제어 `01 03` | 2 B | 2 B | 0 |
| 메시지 2 | 51 B | **45 B** | **−6** |
| 구간 합계 | 90 B | 90 B | 0 |

```
소녀「정겨워라            ← 원본 33B 자리에 39B
　언제나　그리운　풍경。

　드디어　돌아왔구나。      ← 원본 51B 자리에 45B
　１년만의　고향……。
```

### 판정 기준

- **두 메시지 다 정상 출력** → 이 구간에 절대 오프셋 참조가 없다.
  ⇒ **구간 총량만 지키면 메시지끼리 예산을 주고받을 수 있다.** 번역 설계가 훨씬 자유로워진다.
- **두 번째가 깨지거나 진행이 멈춤** → 어딘가 절대 오프셋이 있다.
  ⇒ 모든 메시지를 «원본과 정확히 같은 길이»로 맞춰야 하고, 부족분은 포인터/오프셋
  테이블을 찾아내는 다음 조사로 넘어간다.

### 확정된 번역 설계 규칙

1. 메시지 하나하나를 원본 길이에 맞출 필요는 없다. **재조립 구간의 총 바이트만 보존**한다.
2. 재조립 구간은 «앞뒤로 확실한 경계가 있는 곳»에서 끊는다.
   현재 방식은 `(start, end)` 를 주고 그 안을 `str`/`raw` 항목으로 완전히 다시 만드는 것.
   `tools/build_poc.py` 의 `REGIONS` 구조가 그대로 본 빌드의 뼈대가 된다.
3. ⚠️ 아직 **구간을 넘어서는 이동**(예: 장면 전체를 밀어 파일 크기를 바꾸는 것)은
   확인되지 않았다. 필요해지면 그때 별도 실험으로 판정한다.
4. ⚠️ 확인된 범위는 «한 구간 90바이트 안에서 ±6바이트». 훨씬 큰 이동이 필요하면
   같은 방식으로 더 넓은 구간을 재조립해 다시 확인할 것.
